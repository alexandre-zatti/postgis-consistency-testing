--- comment dr-jts 2024-04-08T05:23:36Z
This is not a bug, but a limitation in the ability to compute the relate matrix due to numeric rounding.  In order to correctly compute the relate matrix for two lines the **node point** must be computed (see https://github.com/locationtech/jts/issues/396 for an example of a case which requires noding for correct evaluation). However, due to numeric roundoff the computed node point equals an **endpoint** of line B, even though the robust `Orientation` test reports that it lies in the **interior** of B.

It's not clear that there is an algorithm which can avoid noding, since this would cause an inconsistency in other cases.

Another future option is to support evaluating predicates with a distance tolerance.  This will essentially allow avoiding inconsistency due to roundoff.  (However, note that this may not be a solution in itself - when used as part of a bigger process, the entire process must be designed to support using a tolerance.)

--- comment dr-jts 2025-01-10T21:35:09Z
The cause of the `union` anomaly is the [heuristic code](https://github.com/libgeos/geos/blob/main/src/geom/Geometry.cpp#L623) in `Geometry::Union`, which combines the two inputs if their envelopes are disjoint.  It does not check for empty geometries (and in general does not reduce geometries to a more canonical form, which performing an explicit union would do).

This code should be enhanced to remove empty elements.  

Actually I'm in favour of removing it altogether, since it creates other behaviour differences with OverlayNG (for example, it does not node disjoint sets of LineStrings).  Or at least refining it significantly, and perhaps moving it into OverlayNG, since it is then available everywhere.  At very least it can be moved into `HeuristicOverlay`.

In general I think it's better to avoid putting heuristic logic into `Geometry` methods, because:
* complex heuristic logic complicates the `Geometry` class
* it splits up the logic for operations and makes it less widely available

===== geos_1523.json open None | Overlay silently wrong when an operand has a zero-width collinear interior ring | milestone: None | closed None
# Overlay silently returns wrong areas when noding a nearly collinear interior ring

Intersection and difference of two valid polygons can silently return incorrect areas when one polygon has an extremely thin triangular hole and the other polygon's boundary crosses it. The floating-point overlay returns successfully, so the robust overlay wrapper does not retry.

## Reproduce

Save these geometries as `a.wkt` and `b.wkt`, respectively:

```text
POLYGON ((379.694383 3423, 382 3423, 382 3428, 379.694383 3428, 379.694383 3423))
```

```text
POLYGON ((380 3428.3, 382 3429, 388 3422, 377 3422, 378 3427, 380 3428.3),
         (379.153701 3427.199712952367, 380.736005 3427.1997128766443,
          379.777158 3427.199712922531, 379.153701 3427.199712952367))
```

Both geometries pass `isValid`. A lies inside B's shell. B's hole is nearly collinear, but **not exactly collinear or zero-area**: exact rational arithmetic on the parsed binary64 coordinates gives a hole area of approximately `1.3650878779e-13`.

```sh
geosop -a a.wkt isValid
geosop -a b.wkt isValid
geosop -a a.wkt -b b.wkt -f wkt intersection
geosop -a a.wkt -b b.wkt -f wkt difference
```

Without the fix, intersection returns:

```text
POLYGON ((379.694383 3427.1997129264923, 380.736005 3427.1997128766443,
          379.777158 3427.199712922531, 379.694383 3427.1997129264923))
```

| Operation | Observed area | Expected area, approximately |
| --- | ---: | ---: |
| A intersection B | 5.01746e-15 | 11.528085 |
| A difference B | 11.528085 | 0 |

The exact difference is a tiny portion of the hole, not literally empty. The error is that almost all of A is assigned to the wrong result.

Independently reproduced on GEOS 3.13.1 and the unpatched development revision `55809ca8d` (3.16.0dev). Swapping the inputs also gives incorrect results; for B difference A, the expected area is approximately `36.571915`, rather than approximately `48.1`. Keep the hole's ordinates as written: this example depends on rounding at binary64 precision.

Snap-rounding computes the expected areas for this example:

```sh
geosop -a a.wkt -b b.wkt -f wkt intersectionSR 100000000
geosop -a a.wkt -b b.wkt -f wkt differenceSR 100000000
```

![Input configuration and the local winding reversal after noding](https://github.com/user-attachments/assets/2ffeb7cc-ed16-440d-aa12-196211c61e52)

## What happens

Exact rational calculations on the parsed doubles establish the following numerical mechanism:

1. The two intersections of A's left edge with the hole differ in y by approximately `1.496359985e-13`. One ulp at this y-coordinate is `4.547473509e-13`. Both crossings round to `X = (379.694383, 3427.1997129264923)`.
2. Replacing the crossings with X pinches the hole. The remaining triangle, in vertex order X, second hole vertex, third hole vertex, has signed area approximately `-5.017455576e-15`, whereas the original ring has positive signed area. Its winding has reversed on the noded coordinates.
3. The boundary side labels come from the original ring, while the angular order at X comes from the noded coordinates. This example gets through side-location consistency checking but propagates incorrect locations to A's boundary. Intersection then assembles only the tiny triangle.

The existing result-area heuristic does not detect this case: intersection is checked against upper bounds, which a tiny result satisfies. Difference also satisfies its existing bounds here. This does not imply that every operation's area check is only an upper-bound check.

The unpatched development revision already includes the angular-ordering change from GH-1499. This reproduction therefore needs additional handling beyond that change.

## Proposed fix

After labelling, check for inconsistent edge locations at nodes incident on a collapsed edge. For each eligible non-boundary, non-collapsed edge, compare its label with a point-in-area query against the original input, using a midpoint sample from its longest segment with an eligible midpoint. Skip samples that round to a segment endpoint, are non-finite, or locate on the input boundary. A mismatch raises `TopologyException`, allowing `OverlayNGRobust` to retry with its existing snapping strategies.

**Apply this check only to the default floating-point noding path for linear inputs.** Do not apply it with a fixed precision model, a caller-supplied noder, or curved inputs. Snapping and precision reduction can legitimately change locations relative to the original geometry; rejecting those changes would break the fallback strategies. A supplied noder can snap even when the overlay precision model is floating.

This is a targeted consistency heuristic. It detects the inversion in this reproduction without adding a distance tolerance to the check. It is not a proof that all possible inversions have collapsed edges, nor a complete validation of the overlay graph. The existing robust retries retain their own snapping tolerances.

===== jts_1239.json open None | OverlayNGRobust symDifference returns an inverted polygon: the area check has no lower bound for SYMDIFFERENCE | milestone: None | closed None
For a valid polygon and a valid line crossing near its vertices, `OverlayNGRobust` returns an invalid symmetric difference: the polygon's ring comes back as the *hole* of a tiny shell (area ~1.4e-22), so the result has area −0.03123 instead of 0.03123. Union and difference of the same pair are correct. The cause looks like a gap in `OverlayUtil.isResultAreaConsistent`: for `SYMDIFFERENCE` it only checks the upper bound, so the bad result of the first snapping try is accepted instead of rejected. Reproduces on 1.20.0 and current master (`5a0a7363`); GEOS 3.15.0 and current main return the same result.

## Reproducer

```java
WKTReader reader = new WKTReader();
Geometry a = reader.read("POLYGON ((20.58 46.965, 27.52 53.905, 28.52 54.914, 20.58 46.965))");
Geometry b = reader.read("LINESTRING (27.519999973297118 53.90499997329712, 52.192 78.577, 27.519 53.904, 28.519999999 54.913999999, 39.599 65.984)");

a.isValid(); b.isValid();                                         // true, true
Geometry r = OverlayNGRobust.overlay(a, b, OverlayNG.SYMDIFFERENCE);
r.getArea();                                                      // -0.031229999995478153
r.isValid();                                                      // false

OverlayNGRobust.overlay(a, b, OverlayNG.UNION).getArea();         // 0.03122999999997944, valid
OverlayNGRobust.overlay(a, b, OverlayNG.DIFFERENCE).getArea();    // 0.03122999999997944, valid
```

`b` has no area, so the areal part of `a ⊕ b` should be `a` itself: area 0.03123, valid. The returned polygon instead has a 4-vertex shell of area ~1.4e-22 near (28.52 54.914), and `a`'s ring after snapping (area 0.0312299999955) as its hole. The input is reduced from a fuzzer case; every vertex of `b` is needed.

## What happens

1. Floating-point `OverlayNG` throws `TopologyException` (non-noded intersection), so `OverlayNGRobust` falls back to snapping noding, starting from `snapTolerance(a, b)` = 78.577 / 1e12 = 7.8577e-11 and multiplying it by 10 on each try.
2. The first two tries, with `OverlayNG.overlay(a, b, op, new SnappingNoder(tol))`:

   | tol | SYMDIFFERENCE | UNION | DIFFERENCE |
   |---|---|---|---|
   | 7.8577e-11 (first try) | area −0.03123, invalid — **accepted** | `TopologyException: Result area inconsistent with overlay operation` | same as union |
   | 7.8577e-10 (second try) | 0.03123, valid | 0.03123, valid | 0.03123, valid |

3. On the first try the area check rejects the result for union and difference, so `OverlayNGRobust` moves on and the second try gives the correct answer; for symDifference it accepts the inverted result:

   ```java
   case OverlayNG.SYMDIFFERENCE:
     isConsistent = isLess(areaResult, areaA + areaB, AREA_HEURISTIC_TOLERANCE);
     break;
   ```

   `INTERSECTION` checks only upper bounds, `UNION` only lower ones, and `DIFFERENCE` both. `SYMDIFFERENCE` checks only the upper bound, so a negative (or near-zero) area has nothing to fail against.

## Possible fix

The symmetric difference can't be smaller than the difference of the input areas. Written the way #1005 wrote the lower bound for `DIFFERENCE`, so that nearly identical inputs (whose areas differ only by rounding) still get an empty result:

```java
case OverlayNG.SYMDIFFERENCE:
  isConsistent = isLess(areaResult, areaA + areaB, AREA_HEURISTIC_TOLERANCE)
      && areaResult >= Math.abs(areaA - areaB) - AREA_HEURISTIC_TOLERANCE * Math.max(areaA, areaB);
  break;
```

On master `5a0a7363` with this change: the reproducer returns 0.031229999999978345, valid (equal to union); the input from #951 still gives an empty result, both through `OverlayNGRobust` and through `SnappingNoder(1e-10)` / `SnappingNoder(1e-6)`; all 2307 tests in `modules/core` pass. A plainer `isGreater(areaResult, Math.abs(areaA - areaB), AREA_HEURISTIC_TOLERANCE)` is not enough: on the #951 input it rejects the correct empty result (`|areaA − areaB|` = 8.9e-16) and throws `Result area inconsistent`. The same change in GEOS 3.15.0's `OverlayUtil::isResultAreaConsistent` fixes the reproducer there too and keeps the #951 input empty.

This only fixes the safety net — the first snapping try still builds an inverted polygon, which may be worth a look on its own.
